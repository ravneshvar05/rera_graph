Here are **clear points explaining why the standard GraphRAG pipeline cannot be directly applied to our residential brochure system**, and why our custom Vision -> JSON -> Deterministic Graph approach is superior.

---

## 1. GraphRAG is Designed for Narrative Text Data
The Microsoft GraphRAG pipeline was originally developed for **large narrative documents** such as reports, articles, transcripts, or emails. These datasets contain long, continuous textual explanations where entities and relationships must be **discovered from text using language models**.

In contrast, our dataset of residential project brochures consists mostly of **images, diagrams, floor plans, and visual layouts**, with very little continuous narrative text. Because of this, the standard GraphRAG open-ended indexing pipeline (text chunking → entity extraction → graph construction) cannot operate effectively on our visual content.

---

## 2. Lack of Selectable or Structured Text
Standard GraphRAG fundamentally relies on **text chunking**, where large documents are split into smaller word blocks (e.g., 500-word chunks) that are passed to an LLM to blindly extract entities.

However, almost all of our real estate brochures are **scanned PDFs where the text is non-selectable and embedded inside images or layout diagrams**. Critical information—such as room sizes, unit configurations, directional facings (Vastu), or amenities—is purely graphical. Standard chunking and OCR-based text extraction completely fail on floor plans because spatial context is lost.

---

## 3. Information is Primarily Visual Rather Than Linguistic
In residential brochures, key information is conveyed through **visual representations**, such as:
* Unit layout diagrams
* Floor plans
* Master plans of the society
* Compass roses (for determining entrance facing)

GraphRAG assumes information is expressed **linguistically in sentences**. In our system, the information must first be interpreted holistically from **visual elements using Multimodal Vision-Language Models (like Gemini 1.5/2.5 Pro/Flash)** before any graph can be created.

---

## 4. Entity Structure is Already Known (Fixed Schema vs. Open Discovery)
In GraphRAG, entities and relationships are **discovered dynamically by an LLM** from unstructured text (e.g., it might invent a relationship like `HAS_FEATURE` one time, and `CONTAINS_AMENITY` the next).

In our residential brochure domain, the structure is already rigidly defined. Our core entities are known:
* Project
* Developer
* Location (City, Neighbourhood)
* Unit Type (2BHK, 3BHK)
* Rooms (Master Bedroom, Kitchen, etc. with strict float dimensions)
* Amenities

Since our schema is highly predictable, entities and relationships can be **directly mapped into structured JSON rather than guessed through open-ended LLM extraction**. This guarantees a clean, queryable Neo4j schema without the hallucination risks of standard GraphRAG.

---

## 5. Structured Extraction is Deterministic and Mathematically Reliable
Because we use a vision model to first extract the brochure into a strictly typed Pydantic JSON format, the resulting data already contains **explicit, clean fields and relationships** (e.g., ensuring `carpet_area_sqft` is always a float).

Running GraphRAG’s open-ended entity extraction would introduce **redundant processing, astronomical API clustering costs, and the inability to run hard mathematical filters** (like `WHERE Unit.area_sqft > 1000`). Our deterministic Python script (`kg_ingest.py`) builds the graph instantly and perfectly from the JSON.

---

## 6. Required Architectural Pipeline Shift
To successfully process our brochure data, we have replaced the standard Text-GraphRAG indexing pipeline with a **Multimodal-Structured pipeline**:

```
[Scanned Brochure PDF]
         ↓  (Multimodal Vision LLM - gemini.py)
[Strictly Typed Pydantic JSON]
         ↓  (Deterministic Python Ingestion - kg_ingest.py)
[Perfectly Schematized Neo4j Knowledge Graph]
```

This preprocessing stage is required because the original GraphRAG indexing pipeline assumes the input data is purely textual and unstructured, which does not apply to our visually-complex real estate domain.

---

✅ **Summary for Presentations/Reports**
The conventional GraphRAG approach cannot be directly applied to our real estate dataset because the information is primarily visual, lacks continuous machine-readable text, and follows a predictable, highly-structured schema. Therefore, we utilize a modified pipeline where a Multimodal Vision-Language Model first converts the scanned brochure graphics into strict JSON structured data, after which the Knowledge Graph is deterministically constructed using programmatic Neo4j ingestion, ensuring zero hallucination in the database layer.
