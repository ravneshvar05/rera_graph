1 Overview of the Architecture

This repository orchestrates a robust "Hybrid GraphRAG" architecture tailored for real‑estate data. It combines a deterministic Knowledge Graph (Neo4j) with a semantic Vector Store (ChromaDB). The LLM is only used for intent parsing and answer synthesis.

💡

The Core Philosophy: Real‑estate data is already a graph. By storing it directly in Neo4j we guarantee 100 % accuracy on structured queries (e.g., "3 BHK in Bopal").

2 Entity & Relationship Extraction – Why No LLM?

Standard GraphRAG tutorials let an LLM extract entities from raw text. We avoid this for three reasons:

  1. Structural Certainty: Deterministic mapping via Python parsers guarantees no hallucinations.
  2. Zero Data Loss: Every field from the JSON brochure is written verbatim to Neo4j.
  3. Compute Efficiency: MERGE‑based ingestion runs in seconds, whereas LLM extraction would be minutes per brochure.
⚠️

Clustering: We deliberately omit community‑detection clustering (Leiden/Louvain) because home‑buyers need precise facts, not thematic summaries.

3 The Step‑by‑Step Pipeline Flow

1
Data Ingestion – Graph Building
📁 kg/kg_ingest.py

This script converts raw JSON brochures into both Neo4j and ChromaDB:

  • JSON Structuring: Iterates over every brochure.
  • Rule‑Based Classification: Uses regex to label amenities (e.g., "Gymnasium" → SPORTS) and landmarks (e.g., "Delhi Public School" → EDUCATION).
  • Idempotent MERGE: Guarantees safe re‑runs – no duplicate Project, City, etc.
  • Vector Document Creation: Builds a rich text block per Unit and embeds it with all‑MiniLM‑L6‑v2 into ChromaDB.
2
Geographic Enrichment
📁 kg/kg_geo_enrich.py

Runs once after ingestion to add spatial intelligence:

  • Zone Linking: Creates Zone → Neighbourhood → City hierarchy.
  • Landmark ↔ Neighbourhood (SAME_AS): Links landmarks to their neighbourhoods.
  • Alias Resolution (ALIAS_OF): Handles spelling variants (e.g., "Vizol" → "Vinzol").
3
Query Intent Parsing
📁 graphrag/graphrag_intent.py

The LLM is invoked here to translate a natural‑language query into a strict QueryIntent schema:

  • Pydantic Enforcement: Guarantees fields like city, bhk, amenities, etc.
  • Fact vs. Semantic Separation: Hard facts go to Neo4j, fuzzy keywords go to the vector store.
4
Dual Retriever
📁 graphrag/graphrag_retriever.py

Executes two parallel retrieval strategies and merges results:

  • Graph Retrieval (Cypher Builder): Dynamically builds a Cypher query from the intent, supporting location, BHK, amenity‑to‑flag mapping, and landmark types.
  • Vector Retrieval (ChromaDB): Uses the raw query plus semantic keywords to perform similarity search, applying exact metadata filters when possible.
  • Merge & Rank: Projects found by both sources are prioritized; results are sorted by source priority then score.
5
LLM Answer Generation & UI
📁 graphrag/graphrag_answer.py & graphrag_app.py

The final step synthesises a user‑facing answer:

  • Strict Grounding: System prompt forces the LLM to use only the retrieved context.
  • JSON Output: Guarantees {"general_summary":..., "projects": [...], "conclusion":...} for the Streamlit UI.
  • Fallback Path: If the LLM call fails, a deterministic fallback builds simple markdown reasoning.
  • Streamlit Front‑End: Renders project cards with source tags (graph, vector, both) and optional debug panels.

4 Verification & Testing

All components are covered by unit tests (not shown). Manual verification steps:

  1. Run python kg_schema.py – ensure constraints are created without errors.
  2. Execute python kg_ingest.py on a sample brochure – check Neo4j node counts and ChromaDB document count.
  3. Run python kg_geo_enrich.py --reset – verify PART_OF, SAME_AS, ALIAS_OF relationships appear.
  4. Start the Streamlit app (streamlit run graphrag_app.py) and test the example queries. Cards should display correct source tags.
  5. Inspect the JSON returned by graphrag_answer.py – it must conform to the schema defined in the system prompt.
