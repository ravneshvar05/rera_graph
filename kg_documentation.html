1 What is a Knowledge Graph?

A Knowledge Graph is a way of storing information as a network of connected entities. Instead of rows and columns, data lives as nodes (things) and relationships (how those things are connected).

Think of it like a map of knowledge. A city has neighbourhoods. Neighbourhoods contain projects. Projects are built by developers, have unit variants, and each unit has rooms. Landmarks sit near projects. This entire web of facts is the knowledge graph — and because the connections are stored directly, you can traverse from any point to any other by following the edges.

🔍

A simple example: To answer "What apartments are in West Ahmedabad with a gym?", a knowledge graph does not search text — it literally walks the graph: find the Zone node called "West Ahmedabad" → follow edges to Neighbourhood nodes → follow edges to Project nodes → follow edges to Amenity nodes and check for "gym" → return the matching projects. Each step is a relationship hop, not a keyword match.

The Building Blocks

Every knowledge graph has three core concepts:

Concept What it is Example from RERA
Node An entity / a thing KP Villas, Bopal, KP Sanghvi, Pooja Room
Relationship A named connection between two nodes KP Villas LOCATED_IN Gokuldham
Property An attribute on a node or relationship Unit: bhk=4, property_type="VILLA", area=918 sqft

The database used here is Neo4j, the most widely adopted graph database. It stores all nodes and relationships, and is queried using a language called Cypher — designed specifically for graph traversal.

2 Why a Knowledge Graph for Property Search?

Real estate data from brochures is already a graph. A project has a developer. It sits in a neighbourhood. That neighbourhood belongs to a broader city zone. The project offers unit variants. Each variant has rooms. The project is near landmarks. It provides amenities.

All of these are natural, meaningful connections — not isolated columns in a table. A knowledge graph preserves and exploits these connections. The result is a system that understands structure rather than relying on text matching for questions that are fundamentally geographic and relational.

What this enables that is otherwise difficult

User Query How the Graph Handles It
"Projects in West Ahmedabad" Traverse Zone → Neighbourhood → Project. West Ahmedabad is a real node in the graph.
"Near Karnavati Club" Follow the NEAR relationship from the Landmark node to Projects. Exact fact, not a text guess.
"Villa with pooja room and terrace" Room types are real nodes — traverse Unit → HAS_ROOM → Room. The room's floor level and dimensions come with it.
"What else did this developer build?" One hop: Developer → BUILT → all Projects.
"With jogging track" or "with swimming pool" Each amenity is stored as its own named node — match by name.

3 The Graph Model

The graph is built from nine types of nodes, each representing a meaningful real-world entity extracted from the brochures.

Node Types

:Project
project_id, project_name, developer_name, rera_number, project_status, possession_date, total_buildings, total_villas
:Unit
unit_id, unit_type, property_type, bhk, entrance_facing, carpet_sqft, super_builtup_sqft, description
:Room
room_type, name, area_sqft, floor_level, attached_bathroom, has_balcony_access
:Neighbourhood
name (normalised locality — e.g. "Bopal", "Vatva", "Nikol")
:Zone
name (broad city zone — "West Ahmedabad", "East Ahmedabad"…)
:City
name (Ahmedabad, Surat, Rajkot, Vadodara…)
:Developer
name (normalised builder company name)
:Landmark
name, landmark_type (EDUCATION / HEALTHCARE / COMMERCIAL / RELIGIOUS / TRANSPORT / RECREATION)
:Amenity
name (actual amenity name — "Swimming Pool", "Jogging Track", "Children's Play Area"…)
✅

De-duplication through MERGE: Shared entities are stored once, regardless of how many brochures mention them. "Ahmedabad" is a single City node. "Bopal" is a single Neighbourhood node. This means adding a new project takes seconds — it simply creates new edges to existing shared nodes.

Relationships

Relationships are the intelligence of the graph. They are named, directional connections that carry meaning on their own.

  • (Project) -[:LOCATED_IN]→ (Neighbourhood) Where the project physically is
  • (Neighbourhood) -[:PART_OF]→ (Zone) The neighbourhood belongs to a city zone
  • (Zone) -[:IN_CITY]→ (City) Zone belongs to a city
  • (Project) -[:IN_CITY]→ (City) Direct shortcut for city-level queries
  • (Project) -[:BUILT_BY]→ (Developer) Who built the project
  • (Project) -[:HAS_UNIT]→ (Unit) Each unit variant in the project
  • (Unit) -[:HAS_ROOM]→ (Room) Each room inside a unit
  • (Project) -[:NEAR]→ (Landmark) Landmarks near the project (from brochure)
  • (Project) -[:HAS_AMENITY]→ (Amenity) Amenities the project offers
  • (Landmark) -[:SAME_AS]→ (Neighbourhood) "BOPAL" landmark → Bopal neighbourhood
  • (Neighbourhood) -[:ALIAS_OF]→ (Neighbourhood) Normalises neighbourhood spelling variants automatically

4 The Search Pipeline

The pipeline processes a user query through five distinct stages, combining structured graph retrieval with semantic vector search to produce a ranked set of project recommendations, which are then turned into a natural‑language answer by an LLM.

Stage 1
Intent Planner
LLM parses the natural‑language query into a structured QueryIntent (e.g., property type, BHK, required amenities, location).
Stage 2A
Graph Traversal
Neo4j Cypher queries are generated from the QueryIntent, retrieving exact matches such as projects in the specified zone with required amenities and rooms.
Stage 2B
Vector Search
ChromaDB performs semantic similarity search on unit embeddings, retrieving projects that match the query in a fuzzy manner (e.g., based on keywords like “spacious”, “near park”).
Stage 3
Merge & Rank
The results from Neo4j and ChromaDB are merged, de‑duplicated, and scored (graph matches receive higher weight). The top‑K projects are selected for answer generation.
Stage 4
Answer Generator
The selected context is fed to the LLM (Groq/Gemini) which generates a JSON‑structured answer containing recommendations, reasoning, and a summary for the UI.
graph LR Q[User Query] -->|Parse Intent| I[Intent Planner] I -->|Cypher Query| G[Graph Traversal (Neo4j)] I -->|Embedding Search| V[Vector Search (ChromaDB)] G --> M[Merge & Rank] V --> M M --> A[Answer Generator (LLM)]
Fig 1. End‑to‑end dual‑retrieval pipeline.

Stage 1 — Intent Planning

A Large Language Model (Groq or Gemini) reads the user's natural language query and extracts a structured intent using a strict Pydantic schema (QueryIntent). The model maps user descriptions to specific fields like city, neighbourhood, bhk, property_type, amenities, and specific_landmarks. This structured intent acts as the blueprint for the downstream retrieval.

For example, "4 BHK villa near Karnavati Club with gym and pooja room" becomes:

Field in QueryIntent Extracted Value
property_type "VILLA"
bhk 4
specific_landmarks ["Karnavati Club"]
amenities ["gym", "pooja room"]
query_type "SPECIFIC"

Stage 2A — Graph Traversal

The graph traversal answers the structural part of the query — location, BHK, property type, room types, and amenities — by walking the graph's edges. The answer comes from the stored relationships, not from text matching. This is the key advantage: the result is provably correct because it follows actual facts in the data.

Stage 2B — Vector Search

ChromaDB holds a semantic embedding for every unit in every project. The semantic query is used to find units whose descriptions are most similar in meaning — regardless of the exact words used. This handles vague queries like "spacious villa with good ventilation" or "affordable apartment near schools" where structure alone is not enough.

The vector search is pre-filtered by city and zone so it only scans the relevant region, not the entire dataset.

Stage 3 — Merge and Rank

Results from Neo4j and ChromaDB are combined into a single, deduplicated list. Instead of a complex weighted sum, projects are ranked primarily by their source of retrieval (Graph vs. Vector vs. Both):

Priority Level Retrieval Source Description
High (Priority 0) Found in Both (Graph + Vector) Project precisely matches structural requirements (Neo4j) and is semantically highly relevant (ChromaDB).
Medium (Priority 1) Graph Only Project precisely matches structural filters (e.g. Zone, BHK) but falls short on semantic keyword matching.
Low (Priority 2) Vector Only Project has high semantic similarity but lacks exact structured data connections (useful for vague/fuzzy queries).

Within each priority tier, projects are tie-broken by their ChromaDB vector distance score (lower distance is better). The top-K unique projects (defined by FINAL_TOP_N) are then passed as context to the LLM for answer generation.

bhk=3, specific_landmarks="Karnavati Club",
amenities="jogging track" par Graph + Vector run together QP->>KG: Traverse graph for matching projects KG-->>QP: [KP Villas, Swastik Park...] and QP->>VEC: Semantic similarity search VEC-->>QP: [(project_id, distance), ...] end Note over QP: Merge by Priority (Both, Graph, Vector) & Rank QP->>AG: Top projects with full context AG->>U: JSON-structured answer
Fig 3. Full query flow showing parallel graph and vector search

Stage 4 — Answer Generation

Finally, the top-ranked projects are compiled into a rich text context and sent to the LLM alongside the original user query. The Answer Generator strictly filters out any context that contradicts the user's hard constraints (preventing hallucinations). The LLM synthesises this data into a structured JSON response containing the matching project IDs, a natural-language explanation of why they match, and a summary. The Streamlit frontend uses this JSON to render interactive project cards for the user.

5 Data Ingestion

Ingestion is the process of reading each brochure JSON file and writing its data into the graph. Every write operation uses the graph's MERGE pattern — which means it is safe to run more than once. Re-running ingestion on an already-ingested project simply updates it rather than creating a duplicate. This makes the system idempotent.

What happens to each brochure

When a brochure is ingested, the following entities are created or connected in order:

Step What is created How
1 City and Neighbourhood nodes MERGE — shared across all projects in the same area
2 Developer node MERGE — one node per unique builder name
3 Project node MERGE on project_id. Connected to City, Neighbourhood, Developer
4 Landmark nodes MERGE on normalised name. Connected via NEAR. Typed by category.
5 Amenity nodes MERGE on normalised amenity name. Connected via HAS_AMENITY.
6 Unit nodes MERGE on unit_id. Connected to Project via HAS_UNIT.
7 Room nodes Created fresh per unit. Connected via HAS_ROOM. Stores room type, dimensions, floor.
8 ChromaDB embedding Rich text built from unit details is embedded and stored in ChromaDB for vector search

Parallel Processing

For 20,000 brochures, ingestion runs with multiple worker threads — typically 8 to 16. Neo4j handles concurrent writes natively through its transaction model. ChromaDB upserts are batched for efficiency. A progress log is emitted every 100 files so the operator can monitor rate and catch failures early.

Null Project IDs

Some brochures from OCR extraction have a missing or null project ID. These are handled with a deterministic fallback: a stable identifier is built from the project name and source filename, so every brochure always gets a unique, repeatable ID even without one in the source data.

The Landmark Typing System

Landmarks extracted from brochures are noisy OCR text. At ingestion time, each landmark name is classified into one of six types by checking for key words in the name. This allows users to later ask "what schools are near KP Villas?" — a query that would be impossible without typed landmarks.

Type Recognised by words like
EDUCATION school, college, vidyalaya, university, institute
HEALTHCARE hospital, clinic, medical, health centre
COMMERCIAL mall, bazaar, market, shopping, republic
RELIGIOUS mandir, temple, masjid, derasar, church
TRANSPORT bus stop, railway, metro, AMTS, station
RECREATION club, park, garden, ground

6 Geographic Understanding

One of the most powerful aspects of the knowledge graph approach is how it encodes geographic hierarchy. A user saying "in West Ahmedabad" is making a statement about a zone — not a street or building. The graph understands this through its structure.

Zone Hierarchy

After initial ingestion, a one-time enrichment script builds the Zone layer of the graph. Each neighbourhood extracted from the brochures is linked to the Zone it belongs to. This creates a three-level hierarchy:

graph LR City["City\nAhmedabad"] --> Z1["Zone\nWest Ahmedabad"] City --> Z2["Zone\nEast Ahmedabad"] City --> Z3["Zone\nSouth Ahmedabad"] Z1 --> N1["Neighbourhood\nBopal"] Z1 --> N2["Neighbourhood\nSatellite"] Z1 --> N3["Neighbourhood\nGokuldham"] Z2 --> N4["Neighbourhood\nNikol"] Z2 --> N5["Neighbourhood\nNaroda"] Z3 --> N6["Neighbourhood\nVatva"] Z3 --> N7["Neighbourhood\nSarkhej"]
Fig 4. Geographic hierarchy in the graph — City, Zone, Neighbourhood

Because this hierarchy is encoded as graph edges, a query for "West Ahmedabad" automatically includes all projects in Bopal, Satellite, Gokuldham, and every other neighbourhood linked to that Zone — with no extra logic needed at query time.

Landmark–Neighbourhood Cross-linking

Brochures often list well-known area names as "nearby landmarks" — for example, KP Villas lists "BOPAL" as a landmark. The enrichment script detects when a landmark name matches a known neighbourhood and creates a SAME_AS edge between them. This means a search for "projects near Bopal" correctly finds KP Villas even though Bopal is listed as a landmark, not as its address.

Spelling Aliases

Different brochures (and different users) spell the same area differently. The enrichment step encodes known variants as ALIAS_OF edges. When a user searches "Vizol", the graph traverses the alias edge to "Vinzol" and returns all matching projects — with no hardcoded dictionary needed at query time.

⚠️

Zone mapping is data, not code: The Zone → Neighbourhood mappings are maintained as a configuration file that can be updated without code changes. As new project areas emerge in the city, simply adding the neighbourhood-to-zone mapping in the config and re-running the enrichment script is all that is needed.

7 How Amenities Are Handled

Amenities are stored as individual named nodes in the graph. Each unique amenity — "Swimming Pool", "Jogging Track", "Children's Play Area", "Gymnasium" — gets its own :Amenity node. Projects connect to their amenity nodes via a HAS_AMENITY relationship.

💡

Why individual names? A user saying "with jogging track" should get results for projects that have a jogging track — not a vague sports category. Storing actual amenity names means the query planner can extract the user's exact words and the graph can match them directly, supporting any amenity a user might ask about.

Normalisation at Ingestion

Because different brochures describe the same amenity differently — "Jogging Track", "Running track", "jogging path with lights" — the ingestion pipeline normalises amenity names to a consistent form before storing them. This is done through a lightweight normalisation map that converts known variants to a canonical name.

Examples of how raw amenity text gets normalised:

Raw text from brochure Stored as
"Jogging track amidst the landscaped COP" Jogging Track
"Running track" Jogging Track
"A well-equipped gymnasium and health club" Gymnasium
"Gym" Gymnasium
"Swimming pool with changing area" Swimming Pool
"Children's play zone with equipment" Children's Play Area
"A netted sports zone for volleyball and cricket" Sports Court
"Indoor sports room" Indoor Sports Room
"Power backup for all common areas" Power Backup
"Exclusively gated community with hi-tech security" Gated Community

Searching Amenities

When a user asks about an amenity, the query planner extracts the amenity term from their message. The graph search then finds all amenity nodes whose name contains that term — making it flexible for partial matches. "gym", "gymnasium", and "health club" will all match the Gymnasium amenity node. "pool" and "swimming" will both match Swimming Pool.

Examples of representative amenities stored in the graph, drawn from the actual brochure data:

Swimming Pool Gymnasium Jogging Track Children's Play Area Clubhouse Indoor Sports Room Sports Court Landscaped Garden Gated Community Power Backup CCTV Surveillance Parking Celebration Lounge Indoor Games Room Lift

This model is robust — a user can ask for any amenity using their own words, and as long as the match lands on a stored amenity node, results are returned accurately.

8 How Search Works

The graph search translates a structured query intent into a series of relationship traversals. No keyword matching or text scoring is involved for the structured part — the graph either has the fact or it does not.

Location Resolution

Location questions are answered purely through the graph hierarchy:

  • If the user specifies a city (Ahmedabad, Surat…) → match on the City node
  • If the user specifies a zone (West Ahmedabad…) → traverse Zone → Neighbourhood → Project
  • If the user specifies an area (Bopal, Nikol…) → match on Neighbourhood node, also traversing ALIAS_OF edges for spelling variants
  • If the user says "near [place]" → match on Landmark node via the NEAR relationship

Property and Unit Filtering

BHK count, property type (apartment, villa, row house…), area in square feet, and entrance facing are all properties stored directly on the Unit node. These are simple equality or range filters applied during the traversal from Project to Unit.

Room type requirements — "with pooja room", "with terrace", "with servant's quarters" — are resolved by traversing Unit → HAS_ROOM → Room and checking the room_type property of each Room node.

Amenity Matching

The user's amenity term (e.g. "gym", "jogging track") is matched against the name property of all Amenity nodes connected to the project. A partial string match is used so that "gym" matches "Gymnasium" and "pool" matches "Swimming Pool". This is done at the Amenity node level — a single hop from Project.

Developer Portfolio Queries

If a user asks "what has [developer] built?" or "show me projects by [developer]", the Developer node is located first and all Project nodes connected via BUILT_BY are returned. Because the Developer is a real entity in the graph rather than a repeated text field, this query is reliable and immediate regardless of how many projects the developer has.

Query Types

Query Type How it works Example
SPECIFIC Applies structural filters + vector semantic matching. Returns targeted projects matching specific property criteria. "3 BHK apartments in Bopal with a pool"
GLOBAL Bypasses structural filters to return a broad overview of all projects or top-level metrics. Used when no specific intent parameters can be securely identified. "What kinds of projects do you have available?"

Fallback Strategy

If a structured Cypher traversal fails or returns an error, the DualRetriever automatically falls back to a broad graph query (_get_all_projects) to ensure the vector semantic search (which runs in parallel) still has baseline graph project data to merge against. This ensures the app never crashes on a malformed logic combination and always gracefully attempts a fuzzy match.

8 Scaling to 20,000 Brochures

The graph database scales naturally with the data because shared entities are stored once. Adding the 10,000th brochure does not add a 10,000th "Ahmedabad" node — it simply adds a new Project node and edges to the already-existing City, Zone, Neighbourhood, and Developer nodes.

Entity Estimated Count at 20,000 brochures Notes
:Project nodes ~20,000 One per brochure
:Unit nodes ~80,000 Average 4 unit variants per project
:Room nodes ~400,000 Average 5 rooms per unit
:Neighbourhood nodes ~500 De-duplicated, shared across projects
:Landmark nodes ~2,000 De-duplicated, classified by type
:Amenity nodes ~200–300 De-duplicated, matched by name
Total relationships ~1.2 million All edge types combined

At this scale, Neo4j's performance characteristics are:

  • Memory: The entire graph fits comfortably in under 100 MB of RAM
  • Query speed: A 3-hop traversal (Zone → Neighbourhood → Project) completes in 1–5 milliseconds
  • ChromaDB: Approximately 320,000 unit embeddings, pre-filtered by city/zone metadata — so vector search never scans the full dataset
✅

Graph databases are designed for this. Neo4j was built for exactly this kind of connected, multi-hop traversal at scale. The 1.2 million relationships in this system are considered a micro-graph in production Neo4j terms — the same technology runs at billion-edge scale at companies like eBay, Airbnb, and NASA.

9 Deployment Steps

The system is built as a set of focused Python scripts, each with a single responsibility. They are split between the kg/ folder (for building the graph) and the graphrag/ folder (for searching it).

# Script / Action What it does
1 Neo4j Instance Start Neo4j via Docker or Neo4j Desktop. The graph database must be running before any other step.
2 kg/kg_schema.py Creates uniqueness constraints and indexes in Neo4j — ensures fast lookups on project_id, neighbourhood name, amenity name, and BHK count.
3 kg/kg_ingest.py Reads all brochure JSON files and writes to Neo4j + ChromaDB in parallel.
4 kg/kg_geo_enrich.py Runs once after initial ingestion. Builds the Zone → Neighbourhood hierarchy and cross-links landmark nodes to neighbourhood nodes where applicable.
5 graphrag/graphrag_app.py Starts the Streamlit application. This app acts as the orchestrator, importing graphrag_intent.py (query planning), graphrag_retriever.py (graph and vector search), and graphrag_answer.py (LLM generation) to process queries at runtime.
🚀

How to start: Ensure Neo4j is running, then execute the scripts in the kg/ folder sequentially. Once ingestion and enrichment are complete, run streamlit run graphrag/graphrag_app.py from the project root to interact with the Knowledge Graph.

10 Knowledge Graph vs. Tabular Approach

Both approaches have genuine strengths. The table below is an honest assessment of where each excels for this specific real estate domain.

Capability Knowledge Graph Tabular / Relational
Geographic zone queries ("in West Ahmedabad") ✅ Native — Zone is a real node ❌ Zone concept does not exist default
Landmark proximity ("near Karnavati Club") ✅ NEAR relationship — exact fact ⚠️ Text search — false positives
Room type filtering ("villas with terrace") ✅ Room nodes — actual room data ⚠️ Precomputed boolean flags needed
Amenity search ("with jogging track") ✅ Named Amenity nodes — flexible ⚠️ Full-text search on raw strings
Developer portfolio ("what did X build?") ✅ One relationship hop ⚠️ Text JOIN on developer name
Spelling variant handling ("Vizol / Vinzol") ✅ ALIAS_OF edge — encoded permanently ⚠️ Requires manual lookup table
Adding new area / zone without code changes ✅ Add link via graph enrichment ⚠️ Code change required in mapping dictionaries
Fuzzy Semantic Search ("spacious homes") ✅ Supported via ChromaDB integration ❌ Not supported natively
📌

Summary: For questions that are geographic, relational, or multi-hop in nature — which is the majority of real estate search queries — the Knowledge Graph is the correct architectural choice.
