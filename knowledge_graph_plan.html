RERA Chatbot — Knowledge Graph Plan

💡

The core insight: Brochure data is already a graph. A project has a developer, sits in a neighbourhood that belongs to a zone, has unit variants, each with rooms. Landmarks exist near projects. Amenities belong to categories. A Knowledge Graph keeps this structure intact and queries it through relationships — not text matching.

The Graph Model

Node Types

:Project
project_id, project_name, developer_name, rera_number, project_status, possession_date, total_buildings
:Unit
unit_id, unit_type, property_type, bhk, entrance_facing, carpet_sqft, super_builtup_sqft, description
:Room
room_type, name, area_sqft, floor_level, attached_bathroom, has_balcony_access
:Neighbourhood
name — normalised locality (Bopal, Vatva, Nikol…)
:Zone
name — broad zone (West Ahmedabad, East Ahmedabad…)
:City
name — Ahmedabad, Surat, Rajkot…
:Developer
name — normalised builder name
:Landmark
name, landmark_type (EDUCATION / HEALTHCARE / COMMERCIAL / RELIGIOUS / TRANSPORT / RECREATION)
:Amenity
name — the actual amenity name, e.g. "Swimming Pool", "Jogging Track", "Gymnasium", "Gated Community", "Children's Play Area"

Relationships

(Project)-[:LOCATED_IN]-->(Neighbourhood)
(Neighbourhood)-[:PART_OF]-->(Zone)
(Zone)-[:IN_CITY]-->(City)
(Project)-[:IN_CITY]-->(City)
(Project)-[:BUILT_BY]-->(Developer)
(Project)-[:HAS_UNIT]-->(Unit)
(Unit)-[:HAS_ROOM]-->(Room)
(Project)-[:NEAR]-->(Landmark)
(Landmark)-[:SAME_AS]-->(Neighbourhood)       -- "BOPAL" landmark links to Bopal neighbourhood
(Neighbourhood)-[:ALIAS_OF]-->(Neighbourhood) -- "Vizol" → "Vinzol"
(Project)-[:HAS_AMENITY]-->(Amenity)          -- individual named node
✅

Rooms as real nodes (not flags): Each room is a graph node with its own properties. Querying (u)-[:HAS_ROOM]->(r:Room {room_type: "POOJA_ROOM"}) returns the actual room — with dimensions, floor level, and bathroom access — in the same traversal. No precomputation. No schema changes if you add new room types later.

✅

Individual Amenity nodes, not fixed categories: Each amenity is stored with its actual name — "Swimming Pool", "Jogging Track", "Gymnasium". A user can ask about any amenity using their own words. "gym", "gymnasium", and "health club" all resolve to the same Gymnasium node through partial name matching. No rigid category buckets — robust for any phrasing.

Ingestion Pipeline — kg_ingest.py

Amenity Classification (runs at ingestion, not at query time)

AMENITY_CATEGORIES = {
    "SPORTS":         {"gym", "swimming", "pool", "jogging", "running", "sports",
                       "cricket", "volleyball", "basketball"},
    "WELLNESS":       {"health club", "spa", "yoga", "meditation", "health"},
    "SECURITY":       {"security", "cctv", "gated", "guard", "surveillance"},
    "NATURE":         {"garden", "park", "landscap", "green", "tree", "lawn"},
    "SOCIAL":         {"clubhouse", "lounge", "party", "community", "children play"},
    "INFRASTRUCTURE": {"power backup", "parking", "generator", "lift", "water"},
}

def classify_amenity(text: str) -> str:
    lower = text.lower()
    for category, keywords in AMENITY_CATEGORIES.items():
        if any(kw in lower for kw in keywords):
            return category
    return "OTHER"

Landmark Classification (runs at ingestion)

def classify_landmark(name: str) -> str:
    lower = name.lower()
    if any(w in lower for w in ["school", "college", "vidyalaya"]):   return "EDUCATION"
    if any(w in lower for w in ["hospital", "clinic", "medical"]):     return "HEALTHCARE"
    if any(w in lower for w in ["mall", "bazar", "republic"]):         return "COMMERCIAL"
    if any(w in lower for w in ["mandir", "temple", "masjid"]):        return "RELIGIOUS"
    if any(w in lower for w in ["bus stop", "railway", "amts"]):       return "TRANSPORT"
    if any(w in lower for w in ["club", "park", "ground", "garden"]):  return "RECREATION"
    return "OTHER"

Core Cypher MERGE (idempotent — safe to re-run)

-- Project, city, neighbourhood — all wired in one block
MERGE (city:City {name: $city})
MERGE (hood:Neighbourhood {name: $neighbourhood})
MERGE (p:Project {project_id: $project_id})
SET p += {project_name: $name, developer_name: $dev, ...}
MERGE (p)-[:LOCATED_IN]->(hood)
MERGE (p)-[:IN_CITY]->(city)

-- Developer
MERGE (dev:Developer {name: $dev_name})
MERGE (p)-[:BUILT_BY]->(dev)

-- Landmark — classified, cross-linked to neighbourhood
MERGE (lm:Landmark {name: $lm_name})
SET lm.landmark_type = $lm_type
MERGE (p)-[:NEAR]->(lm)

-- Amenity category
MERGE (ac:AmenityCategory {name: $category})
MERGE (p)-[:HAS_AMENITY]->(ac)

-- Unit
MERGE (u:Unit {unit_id: $unit_id})
SET u += {bhk: $bhk, property_type: $ptype, entrance_facing: $facing, ...}
MERGE (p)-[:HAS_UNIT]->(u)

-- Room — CREATE because every room belongs to exactly one unit
CREATE (r:Room {room_type: $rtype, name: $rname, area_sqft: $area, floor_level: $floor})
WITH r MATCH (u:Unit {unit_id: $uid}) CREATE (u)-[:HAS_ROOM]->(r)

Parallel Ingestion

def run_ingestion(workers=8, force=False, dry_run=False):
    driver = GraphDatabase.driver(NEO4J_URI, auth=(NEO4J_USER, NEO4J_PASS))
    json_files = sorted(Path(JSON_DIR).glob("*.json"))

    if force:
        with driver.session() as s:
            s.run("MATCH (n) DETACH DELETE n")  # full graph wipe

    collection = get_chroma_collection()

    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(ingest_one, f, driver, collection, dry_run): f
                for f in json_files}
        for i, fut in enumerate(as_completed(futs), 1):
            fut.result()
            if i % 100 == 0:
                logger.info(f"Progress {i}/{len(json_files)}")
# CLI flags
python kg_ingest.py              # new files only
python kg_ingest.py --force      # wipe + re-ingest
python kg_ingest.py --dry-run    # validate JSON without writing
python kg_ingest.py --workers 16 # parallel thread count

Query Planner — kg_query_planner.py

The LLM is given the graph's own vocabulary — not low-level field names. The system prompt teaches it the concepts:

LOCATION HIERARCHY:
  city       → Ahmedabad, Surat, Rajkot, Vadodara
  zone       → West / East / North / South / Central Ahmedabad
  area       → specific neighbourhood (Bopal, Nikol, Satellite, Sarkhej…)
  landmark   → "near X" place (Karnavati Club, ISCON Temple, Fun Republic…)

AMENITY CATEGORIES:
  SPORTS · WELLNESS · SECURITY · NATURE · SOCIAL · INFRASTRUCTURE

ROOM TYPES (for must_have_rooms):
  BEDROOM · POOJA_ROOM · STUDY_ROOM · TERRACE · SERVANT_ROOM
  DRESSING_ROOM · STORE_ROOM · COURTYARD · BALCONY

PROPERTY TYPES: APARTMENT · VILLA · ROW_HOUSE · TENEMENT · PENTHOUSE

Graph Search — kg_search.py

Zone-based search

MATCH (p:Project)-[:LOCATED_IN]->(n:Neighbourhood)-[:PART_OF]->(z:Zone {name: $zone})
MATCH (p)-[:HAS_UNIT]->(u:Unit {bhk: $bhk, property_type: $ptype})
RETURN DISTINCT p, u, n LIMIT 20

Landmark proximity with amenity filter

MATCH (p:Project)-[:NEAR]->(lm:Landmark)
WHERE toLower(lm.name) CONTAINS toLower($landmark)
MATCH (p)-[:HAS_AMENITY]->(ac:AmenityCategory {name: $amenity_cat})
MATCH (p)-[:HAS_UNIT]->(u:Unit)
RETURN DISTINCT p, u, lm LIMIT 20

Room-type traversal

MATCH (p:Project)-[:HAS_UNIT]->(u:Unit {property_type: "VILLA"})
MATCH (u)-[:HAS_ROOM]->(r1:Room {room_type: "TERRACE"})
MATCH (u)-[:HAS_ROOM]->(r2:Room {room_type: "POOJA_ROOM"})
RETURN DISTINCT p, u LIMIT 20

Developer portfolio — multi-hop

MATCH (d:Developer)-[:BUILT]-(p:Project)-[:LOCATED_IN]->(n:Neighbourhood)
WHERE toLower(d.name) CONTAINS toLower($dev)
RETURN p, n, d ORDER BY p.project_name

Alias-aware area search

MATCH (n:Neighbourhood)
WHERE toLower(n.name) CONTAINS toLower($area)
   OR EXISTS {
       MATCH (n)-[:ALIAS_OF*1..2]->(alias)
       WHERE toLower(alias.name) CONTAINS toLower($area)
   }
MATCH (p:Project)-[:LOCATED_IN]->(n)
MATCH (p)-[:HAS_UNIT]->(u:Unit)
RETURN p, u, n

"Schools near this project" — reverse landmark traversal

MATCH (p:Project {project_id: $pid})-[:NEAR]->(lm:Landmark {landmark_type: "EDUCATION"})
RETURN lm.name AS school

Aggregate count

MATCH (p:Project)-[:LOCATED_IN]->(n:Neighbourhood)-[:PART_OF]->(z:Zone {name: $zone})
MATCH (p)-[:HAS_UNIT]->(u:Unit {bhk: $bhk, property_type: $ptype})
RETURN COUNT(DISTINCT p) AS projects, COUNT(u) AS unit_types

Scoring

Match Type Weight Reason
Exact neighbourhood / zone match 0.7 Project provably in the area
Landmark proximity 0.5 Project is physically near the place
Amenity category match +0.2 bonus Right class of amenity confirmed
Vector similarity (ChromaDB) 0.0 – 0.5 Semantic match on description text
Minimum threshold 0.45 Drops irrelevant results

Knowledge Graph vs. Tabular Approach — Where Each Excels

Query / Need Knowledge Graph (Neo4j) Tabular / Relational
"Projects in West Ahmedabad" ✅ Native — Zone node, one hop through PART_OF ❌ Doesn't exist as a concept in flat tables
"Near Karnavati Club" ✅ Exact — [:NEAR] relationship is a fact ⚠️ Text search — prone to false positives on noisy OCR data
"Villas with terrace and pooja room" ✅ Room nodes — traverse directly to the actual room ⚠️ Boolean flags — precomputed, must be maintained
"With gym" / "with pool" ✅ One hop — [:HAS_AMENITY]->(:AmenityCategory "SPORTS") ⚠️ Text search or boolean flag — inconsistent raw amenity strings
"What else did this developer build?" ✅ One hop — (dev)-[:BUILT]-(project) ⚠️ JOIN on developer name text field
"Schools near KP Villas" ✅ Typed landmarks — {landmark_type: "EDUCATION"} ❌ No concept of landmark type in flat data
"Vizol / Vinzol" spelling variants ✅ ALIAS_OF edge — encoded once, works forever ⚠️ Hardcoded variant list — must be manually maintained
Count / aggregate queries ✅ Cypher COUNT with zone traversal ✅ Strong — COUNT + GROUP BY is a natural fit
Simple exact filters (city = X, bhk = 3) ✅ Works well with indexes ✅ Equally fast with indexes
Bulk export / spreadsheet output ⚠️ Possible but more verbose ✅ Natural fit — rows and columns
Adding new amenity categories or room types ✅ Just add edges — schema-flexible by design ⚠️ Schema change — requires ALTER TABLE or new column
